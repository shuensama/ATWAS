### 这是什么文件？

` .specify/memory/constitution.md` 本质上是你这个项目的「**项目宪章 / 项目宪法模板**」。

- **用途**：  
  - 用来**约定整个项目的核心原则和工作方式**，比如：技术取舍原则、测试要求、集成方式、版本策略、Review 流程等。  
  - 放在 `.specify/memory/` 下，通常是给类似现在这种 AI 助手/自动化工具当作「长期记忆」和「最高准则」，用来指导后续所有规划和实现决策。

- **你现在看到的内容现状**：  
  - 里面有很多占位符：`[PRINCIPLE_1_NAME]`、`[SECTION_2_CONTENT]`、`[GOVERNANCE_RULES]` 等，说明这是一个**尚未填写的模板**。  
  - 注释里的英文示例（Example: ...）是在告诉你可以写些什么，比如：  
    - 核心原则：库优先 / CLI 接口 / 测试优先  
    - 额外约束：安全、性能、合规要求  
    - 工作流：代码评审规则、测试门槛、发布流程  
    - 治理：谁能修改这些规则，修改要走什么流程

- **你应该怎么用它？**  
  - 根据你这个 ATWAS 项目自己的目标和习惯，把这些占位符都替换成**具体、可执行的规则**。  
  - 之后我在帮你写代码、做架构设计或流程设计时，就可以**以这个宪章为「最高规则」**来做决策和检查是否符合。

- **能不能改 / 删？**  
  - **可以自由修改**，而且强烈建议根据你的项目实际情况填完整。  
  - **不建议随便删掉**：删掉不会让项目坏掉，但会失去一个很有用的、让项目「有统一规则」的地方，也会让自动化工具难以理解你的偏好。  

如果你愿意，我可以根据你对 ATWAS 的目标和偏好，帮你**一起把这个宪章文件从模板填成一版初稿**。

- **你什么时候会用到它？**

### 总体说明

这些 `speckit.*.md` 都在 `.cursor/commands/` 里，本质上是 **给 Cursor 里的 AI 定义的一组「工作流命令说明书」**。  
当你在 Cursor 里运行 `/speckit.xxx` 的时候，AI 就会按对应文件里写的步骤去跑（读/写 spec、plan、tasks 等），而不是普通给人看的文档。

---

### 每个文件分别在做什么？

- **`speckit.specify.md`：写规格说明书的入口（建 feature + 写 spec）**  
  - 从你的一句话/一段自然语言需求创建或更新 `spec.md`。  
  - 自动生成 feature 分支（`N-short-name`）、目录、初始 `spec.md` 内容。  
  - 用 `spec-template.md` 填充各必选章节，控制 `[NEEDS CLARIFICATION]` 数量。  
  - 最后还会生成一个「规格质量检查 checklist」，保证 spec 写得够好。

- **`speckit.clarify.md`：专门用来问问题，补 spec 里不清楚的地方**  
  - 在已有 `spec.md` 基础上，扫描哪些地方模糊/缺失（功能、数据模型、性能、安全等）。  
  - 最多问 5 个高价值澄清问题（一次一问），你回答后会 **直接回写到 `spec.md`**，并记录在 `## Clarifications` 里。  
  - 设计目标：在进入 plan 之前，把关键歧义降到最低。

- **`speckit.plan.md`：根据 spec 生成技术实现方案（plan.md）**  
  - 通过 `.specify/scripts/powershell/setup-plan.ps1` 找到当前 feature 的 `spec.md`、`plan.md` 模板等。  
  - 读入宪章 `constitution.md`，在 plan 里做「Constitution Check」。  
  - 生成 `research.md`、`data-model.md`、`contracts/`、`quickstart.md` 等设计类文档。  
  - 最终产物是一个结构化的 `plan.md`，后续会交给 `/speckit.tasks` 拆任务。

- **`speckit.tasks.md`：把 plan/spec 拆成可执行的 tasks.md**  
  - 读取 `spec.md`、`plan.md`（以及 `data-model.md` 等可选文件），按用户故事、阶段生成 `tasks.md`。  
  - 强制任务格式：`- [ ] T001 [P] [US1] 描述 + 文件路径`，包括阶段、依赖、并行标记等。  
  - 目标是：**任何 LLM 或工程师拿着 `tasks.md` 就能直接按顺序实现**。

- **`speckit.analyze.md`：只读分析 spec/plan/tasks 是否一致 & 覆盖完整**  
  - 在 `tasks.md` 已生成的前提下运行，对 `spec.md`、`plan.md`、`tasks.md` 做 **一致性和质量检查**。  
  - 严格只读，不改文件，只输出一份 Markdown 分析报告（表格 + 统计）。  
  - 会重点检查：重复、模糊、未覆盖的需求、违背宪章的地方等，并给出严重级别。

- **`speckit.checklist.md`：针对某个领域生成「需求质量检查清单」**  
  - 基于当前 feature 的 spec/plan/tasks 和你的描述，生成一个 `checklists/*.md`。  
  - 这些 checklist 被视为「**需求写作的单元测试**」，测试的是规格写得好不好，而不是实现对不对。  
  - 支持按 UX/API/性能/安全等领域生成不同清单。

- **`speckit.implement.md`：按照 tasks.md 分阶段自动执行实现工作**  
  - 先检查 `checklists/` 是否都勾完，没勾完会提醒你要不要仍然继续。  
  - 然后读取 `tasks.md`、`plan.md` 等，按 Phase、依赖和 [P] 并行规则 **逐条执行任务**（写代码、建文件等）。  
  - 还会检查/生成 `.gitignore`、`.dockerignore` 等忽略文件。  
  - 每完成任务要把 `tasks.md` 里的对应项从 `[ ]` 改成 `[X]`，最后做收尾验证。

- **`speckit.constitution.md`：更新项目「宪章」的命令**  
  - 负责读取 `.specify/memory/constitution.md` 模板，把里面的占位符填成你项目的核心原则、治理规则。  
  - 根据修改内容自动决定宪章版本号 bump（major/minor/patch），并生成「同步影响报告」。  
  - 同时检查 `plan/spec/tasks` 模板等是否需要跟着宪章更新。

- **`speckit.taskstoissues.md`：把 tasks.md 转成 GitHub Issues**  
  - 在确认远端是 GitHub 仓库的前提下，把 `tasks.md` 里的每个任务，用 GitHub MCP 工具创建对应的 Issue。  
  - 明确禁止对不匹配当前 remote 的其他仓库创建 issue。

### 可以怎么理解这套东西？

可以把你现在这个仓库看成有一整条 **从「一句需求」到「代码落地」的自动化流水线**：

1. `/speckit.specify` → 建分支 + 写 `spec.md`  
2. `/speckit.clarify` → 问关键问题并回写 `spec.md`  
3. `/speckit.plan` → 写 `plan.md` + 设计类文档  
4. `/speckit.tasks` → 生成结构化 `tasks.md`  
5. `/speckit.checklist` → 为需求质量生成专用 checklist  
6. `/speckit.analyze` → 对 spec/plan/tasks 做只读一致性分析  
7. `/speckit.implement` → 按 `tasks.md` 真正去实现代码  
8. `/speckit.taskstoissues` →（可选）把任务同步为 GitHub issues  
9. `speckit.constitution` → 在最上层维护一份长期有效的项目宪章，约束整个流程

    - 新项目刚起，**第一次定「游戏规则」**（核心原则、质量门槛等）。  
    - 已经跑了一阵子，发现工作方式/质量标准要**系统性调整**（比如强制 TDD、增加安全要求），需要版本化的变更。

> 建议：项目初期先跑一遍 `/speckit.constitution`，之后只有当「原则/流程」层面有大改动时才再跑。

## 二、新功能从 0 开始的一条龙流程

### 1. `/speckit.specify` – 建分支 + 写规格说明

- 触发时机：**你有一个新功能的自然语言描述**。  
- 会做的事：  
  - 生成 feature 分支 & `specs/N-short-name/` 目录。  
  - 基于模板写出 `spec.md`（包含需求、场景、成功标准等）。  
  - 顺带生成一个 **spec 质量 checklist**，检查是否满足基本写作质量。

> 用法心智：把它当成「把一句话需求变成一份可沟通的规格文档」的按钮。

---

### 2. `/speckit.clarify` – 问关键问题并写回 spec

- 触发时机：`spec.md` 已有，**但你知道肯定还有模糊点**。  
- 流程：  
  - 自动扫描 `spec.md` 找到模糊/缺失的地方。  
  - 最多问你 5 个 **高价值澄清问题**，一次一问。  
  - 你的回答会立刻被写入 `spec.md`（`## Clarifications` 区块 + 对应章节修改）。

> 建议：**每个重要功能在 `/speckit.plan` 之前至少跑一次 `/speckit.clarify`**，把容易踩坑的歧义先消掉。

---

### 3. `/speckit.plan` – 生成技术方案（plan.md 等）

- 触发时机：spec 和关键澄清差不多搞定后，**准备想「怎么实现」**。  
- 会做的事：  
  - 通过脚本找到当前 feature 的 `spec.md`、`plan.md` 模板等。  
  - 读宪章，做 Constitution Check（有违反会作为 gate）。  
  - 输出：`plan.md`、`research.md`、`data-model.md`、`contracts/`、`quickstart.md` 等。  

> 心智：这是「从需求文档到架构/设计文档」的一步。

---

### 4. `/speckit.tasks` – 从 plan/spec 拆任务

- 触发时机：`plan.md` 已经有了，**准备拆成任务让人/AI执行**。  
- 会做的事：  
  - 读 `plan.md` + `spec.md` (+ 可能的 `data-model.md`、`contracts/` 等)。  
  - 输出结构化的 `tasks.md`，任务按阶段 & 用户故事组织，严格格式如：  
    - `- [ ] T012 [P] [US1] 在 src/models/user.ts 中创建 User 模型`  

> 建议：每个 feature 跑完 `/speckit.plan` 后就紧接着跑 `/speckit.tasks`。

---

### 5. `/speckit.checklist` – 生成针对某领域的「需求质量清单」

- 触发时机：  
  - 想对某个侧重（UX / API / 性能 / 安全等）做 **更深的「需求质量审查」**。  
- 会做的事：  
  - 在 `FEATURE_DIR/checklists/` 下生成对应的 checklist 文件（如 `ux.md`、`api.md`、`security.md`）。  
  - 所有条目都是「检查需求是否写清楚」，不是测试实现。

> 建议：  
> - 规格初稿出炉后，可以先跑一次 `/speckit.checklist`（比如 `ux` 或 `requirements`）。  
> - 在真正实现前，至少保证这些清单基本勾完（这一步会在 `/speckit.implement` 前被检查）。

---

### 6. `/speckit.analyze` – 只读的整体一致性分析

- 触发时机：`tasks.md` 已经生成，**准备实施前想做一次全面体检**。  
- 会做的事：  
  - 读 `spec.md`、`plan.md`、`tasks.md` 和宪章。  
  - 输出一份 Markdown 报告：  
    - 哪些需求重复 / 矛盾 / 模糊  
    - 哪些需求没有任务覆盖  
    - 哪些任务没有对应需求  
    - 哪些地方违背宪章（标为 CRITICAL）  
- 完全 **只读**，不改任何文件。

> 建议：在正式执行 `/speckit.implement` 前跑一次 `/speckit.analyze`，把 CRITICAL/HIGH 问题先消掉。

---

### 7. `/speckit.implement` – 按 tasks.md 分阶段实现

- 触发时机：**准备真的写代码/配置**。  
- 会做的事：  
  1. 先看 `FEATURE_DIR/checklists/` 里的 checklist 是否都有勾完：  
     - 有没勾完的会问你要不要仍然继续。  
  2. 读 `tasks.md`、`plan.md` 等，按 Phase、依赖和 `[P]` 并行标记执行任务。  
  3. 自动维护 ignore 文件（`.gitignore`、`.dockerignore` 等）。  
  4. 每完成一个任务，要求把 `tasks.md` 的 `- [ ]` 改成 `- [X]`。  

> 心智：这是整条流水线里「真正写实现」的那一步，严格按 `tasks.md` 走。

---

### 8. `/speckit.taskstoissues` – 把任务同步到 GitHub Issues（可选）

- 触发时机：  
  - 你希望用 GitHub issues 来管理任务，而不是只看 `tasks.md`。  
- 会做的事：  
  - 先检查 git remote 是不是 GitHub 仓库。  
  - 为 `tasks.md` 中的每个任务创建对应的 Issue（通过 GitHub MCP 工具）。  

> 建议：  
> - 适合团队协作、需要在 GitHub 上做看板/分配任务时使用。  
> - 通常在 `tasks.md` 相对稳定之后再跑。

## 三、已有功能的迭代/修改时怎么走？

如果是 **已经有 spec/plan/tasks 的老功能要改**，典型流程可以是：

1. 直接改 `spec.md` 或跑 **`/speckit.clarify`**，补充/修正需求。  
2. 跑 **`/speckit.plan`** 更新 `plan.md`（以及相关 design 文档）。  
3. 跑 **`/speckit.tasks`** 重新生成/更新 `tasks.md`（视模板和脚本行为而定，注意避免重复）。  
4. 根据需要跑 **`/speckit.checklist`** 和 **`/speckit.analyze`**。  
5. 最后用 **`/speckit.implement`** 完成新增/修改任务。
