### 这些关键文件各自干什么？

- **`package.json`**  
  - **项目清单 & 脚本入口**：列出依赖（比如 `next`, `react`, `typescript`）、`devDependencies`，以及 `scripts`（如 `dev`, `build`, `start`, `lint`）。  
  - `npm install` / `npm run dev` 等命令，都是根据这里来工作的。

- **`next.config.mjs`**  
  - **Next.js 的全局配置文件**，控制框架层面的行为。  
  - 比如：是否启用 App Router、实验特性、`images` 配置、`reactStrictMode` 等，都在这里设置。

- **`tsconfig.json`**  
  - **TypeScript 编译配置**，告诉 TS/编辑器怎么理解你的代码。  
  - 配置路径别名（如 `@/components/*`）、`strict` 模式、`jsx` 处理方式等，影响类型检查和编译结果。

- **`app/layout.tsx`**（App Router 专用）  
  - **全局布局 / 页面骨架**：定义所有页面共享的 HTML 结构（如 `<html>`, `<body>`）、全局样式引入、全局组件（导航栏、页脚等）。  
  - App Router 下每个路由页面都会包在这个布局里面。

- **`app/page.tsx`**  
  - **根路由 `/` 的页面组件**：访问网站根地址（例如 `http://localhost:3000/`）时渲染的页面。  
  - 相当于应用的首页或默认展示内容。

### 各个文件/目录是干什么的？

- **`tailwind.config.ts`**  
  - Tailwind 的**主配置文件**。  
  - 配置哪些文件会被扫描 class（`content`），设计系统（颜色、字号、间距等 `theme` 扩展），以及自定义插件等。  
  - 比如以后你希望有统一的主题色、圆角大小，都在这里配。

- **`postcss.config.mjs`**  
  - 前端 CSS 构建工具 **PostCSS** 的配置文件。  
  - Tailwind 实际上是一个 PostCSS 插件，所以这里会写：`tailwindcss`, `autoprefixer` 等插件。  
  - Next 在构建时会根据这个文件来“预处理”你的 CSS。

- **`app/globals.css`**  
  - 全局样式文件（对整个应用生效）。  
  - 一般会在这里 `@tailwind base; @tailwind components; @tailwind utilities;` 来启用 Tailwind。  
  - 也可以放一些你自己的全局样式（比如全局字体、body 背景色、滚动条样式等）。

- **`components/` 中的基础 UI 目录（比如 `components/ui`）**  
  - 放 **可复用的 UI 组件**，尤其是 shadcn/ui 生成的那些组件（`button.tsx`, `card.tsx` 等）。  
  - 这些组件封装了 Tailwind class，你在页面里只要用 `<Button />` 这种标签，不用每次自己手写一长串类名。  
  - T002 就是要求把这些基础组件搭好，让 `app/(drama-stage)/page.tsx` 可以直接 import 使用。

### 简单回答

- **安装/生成阶段**：  
  你可以一次性把很多（甚至全部）shadcn/ui 组件通过 CLI 加进 `components/ui` 目录里，这是可以的，也不会马上让每个页面的 bundle 变巨。  
- **页面使用阶段**：  
  每个页面/组件文件里，**仍然必须“按需 import”你要用的组件**，比如：

```tsx
import { Button } from "@/components/ui/button";
import { Card } from "@/components/ui/card";
```

没有“全局一次性把所有 shadcn 组件都注入进来然后随便用”的机制。

---

### 更细一点的建议

- **能不能“先全加一遍”？**  
  - 可以，比如你一开始就 `add button card input textarea select ...`，甚至把常用组件全都生成好。  
  - 这样只是让你的 `components/ui` 目录更大一点，对最终前端 bundle 体积没有直接影响，因为打包时只会打进“实际被 import 的组件”。

- **为什么页面里要按需引入？**  
  - React/Next.js 的打包是基于“文件依赖图”的：你 `import` 了哪个组件，它才会被打进当前路由的 JS 里。  
  - 如果你在某个页面里 `import` 了一大堆没用的组件，就会白白增大这个页面的 bundle 体积。

---

### 实际操作建议

- **项目级别**：可以一次性 `add` 常用那几类组件（Button, Card, Input, Tabs, Dialog 等），让目录准备好。  
- **文件级别**：始终只在当前文件里 `import` 真正用到的那几个组件，不要为了“省事”写一个“全部 import 一次”的工具文件到处复用。

**大部分团队是：边用边 `add`，最多一开始先加一小撮“基础组件”。**

---

### 两种做法的对比

- **全部先 `add` 一遍（不太常见）**  
  - **优点**：  
    - 之后不用再跑 CLI，目录里“什么都有”，随时拿来用。  
  - **缺点**：  
    - 目录一下子很大，很多组件你其实不会用到；  
    - 早期还没定好设计语言，就把一堆组件主题/样式都拉进来，后期统一风格要改很多文件。

- **边用边 `add`（主流做法）**  
  - **优点**：  
    - 只引入真的要用的组件，`components/ui` 结构更干净；  
    - 每次 `add` 的时候顺便把这个组件的变体、文案风格一起想清楚，更容易保持一致。  
  - **缺点**：  
    - 第一次用到某类组件时，要停下来跑一遍 CLI，多一步操作。

---

### 结合你这个项目，我的建议

- **当前阶段（单体小应用、PoC 性质）：**
  - 可以 **一次性 add 一组“基础组件”**：`button`, `card`, `input`, `textarea`, `select`, `dialog`, `tabs`, `dropdown-menu`, `toast` 之类；
  - 后面遇到“新交互需求”再 **按需 add 其它组件**（例如 `popover`, `sheet`, `accordion` 等）。
- 这样你：
  - 既有一套够用的基础「舞台控制面板」组件；
  - 又不会一开始就把仓库搞得太膨胀。

如果你告诉我后面大概会有哪些操作（比如“选择剧本”“添加演员”“时间轴控制”等），我可以帮你列一个**适合这个项目的 shadcn 组件组合清单**，顺便标注哪些适合现在就 `add`，哪些留到需要时再加。
